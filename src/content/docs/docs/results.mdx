## What the 49 test prompts are

Every model got the same 49 Omarchy plugin requests. They are held-out test prompts: kept out of Usuba's own training data and
deduplicated against it — no training prompt shares more than half its wording with a test prompt, and no test answer is a
near-copy of a training answer.

They are based on real Omarchy 4 plugins — community plugins, and the kinds of things Omarchy's own shell does. Between them they
cover every plugin type: bar widgets, panels, popups and overlays, menus, background services, and full replacement bars.

| The task | How many |
|----------|----------|
| Write a full plugin from a description | 26 |
| Add a panel to an existing bar widget | 6 |
| Build parts of a larger multi-file plugin | 12 |
| Fix a manifest Omarchy's validator rejects | 5 |

### Full plugins from a description (26)

Everyday bar and shell tools: a clipboard manager, a notification daemon, a weather pill with a popup, a battery and
power-profile widget, brightness controls, an internet speed test, a Dropbox status widget, a desktop background service, and a
Bible verse-of-the-day widget.

Plus recreations of real community plugins: Time Machine (scheduled restic backups), Key Promoter (shows the keyboard shortcuts
in play), Vimarchy (Vim-style window control), Omaland (a Hyprland look-and-feel editor), Intemporel (a clock with calendar
support), Flush Bar, and Port Watch (dev servers in the bar).

### Add a panel (6)

The model is handed an existing bar widget's manifest and asked to extend it with a detail panel: the same widget, now with
somewhere to show more.

### Parts of a larger plugin (12)

Large multi-file plugins, built in pieces rather than all at once: parts of **Beam** (an app launcher and command menu),
**Better Bar** (a dynamic-island-style bar), and **Omarchy Tablet** (Surface tablet mode, with a bar, a service and a menu).

### Fix a broken manifest (5)

Repairing manifests that Omarchy's own validator rejects: a reserved `omarchy.*` id, and entry-point paths that are absolute or
point outside the plugin directory.

## What counts as passing

A plugin passes only when all three hold:

1. the Usuba Checker Scripts pass it,
2. a code read agrees it does the task, with no stubs, fake data or invented APIs, and
3. where we could run it, it loads on the Dell laptop running Omarchy 4.0.4.

Failing doesn't prove a plugin is broken. The Dell load test covered part of the set: 420 plugins passed the scripts at some point
and got a code read. 267 loaded fine, 37 failed and 116 were not run, mostly because the code held destructive commands and we
kept them off the laptop.

## The benchmark

- **49** plugin requests, given to eleven models through **OpenRouter**, with zero data retention on (one exception below).
- When the scripts found problems, their report went back to the model for up to **3** fix rounds.
- Omarchy version: **4.0.4-1**. Run date: **October 16, 2026**.

## The feedback experiment

Give a model the scripts' report and up to three more tries, and more of its plugins pass. These numbers come from the scripts
alone, not from our model.

<UpliftChart />

The scripts help the strong models most: Claude Opus 5.5 went from 14 to 38 passing. Several open models stayed low, and Qwen3.6 27B
didn't gain any. One model passed the scripts on all 49 plugins by its third fix round, yet only 38 survived the code read and the
Dell load test: passing the scripts is not the same as working.

## How this fits with the other exams

The writing test asks whether a model can **write** a plugin. The Usuba Checker Model is judged on three other exams that ask
whether it can **review** one: the Dell 75 (real-hardware verdicts), S4 60 (real bugs mined from git history) and a 329-plugin
holdout from Omarchy plugin reviews. All four are explained, with their limits, on [How Usuba was built and tested](/methodology/#exams).
