Run the Checker Scripts on a plugin before you share it. The feedback is the point, not the score.
</Callout>

## Check a plugin

From the repo, point the script at a plugin folder (the one with `manifest.json`):

```bash
python3 functest/functest.py path/to/your-plugin --reasons
```

| Flag | What it does |
|------|--------------|
| `--reasons` | `PASS` or `FAIL`, then one line per rule hit. Without it you get the full JSON report. |
| `--static` | Static checks only, even where the runtime build exists. |
| `--require-runtime` | Stop with an error if the runtime stage can't start, instead of skipping it. |

The exit code is 0 whether the plugin passes or fails, so read the first line (or the `pass` field in the JSON). An exit code of
2 means the command was used wrong.

## What the Checker Scripts do with it

1. They read the plugin's code against [Usuba Standard v0.2](/docs/standard/) and flag invented APIs, missing programs and
   helper scripts, made-up command flags and fake data.
2. On the reference build, they load the plugin in a real Omarchy shell and catch load errors, crashes and panels that draw
   nothing.
3. They report every problem with a rule id, a plain reason and a fix hint.

## Real output

This is a small "now playing" bar widget with two classic mistakes, checked on a Mac:

```
$ python3 functest/functest.py now-playing --reasons
FAIL (static checks only: runtime skipped, the runtime stage needs Linux, this is darwin)
  [USB-B05] Widget.qml: runs `playerctl` - not an Omarchy/system binary on the Dell and not shipped by the plugin. Fix: use an installed program or ship/document it
  [USB-A04] Widget.qml: line 19: `p.start()` - `Process` has no method `start`. Fix: set `running = true` to start a Process (there is no start())
```

`playerctl` isn't on a stock Omarchy install, and a Quickshell `Process` starts when you set `running = true`; there is no
`start()`. Both are mistakes models make often.
